## Context

`AscendantEmpire.Api/Controllers/UnitDesignController.cs` is 712 lines and carries **22 endpoints**
spanning four different authorization postures (no permission gate, `[Authorize]`, `EntitySetupTool`,
`SystemPanel`) and two architectural styles (MediatR handlers, plus two endpoints that take a
`DbContextFactory` and do raw filesystem I/O). It is the largest controller in the codebase by a wide
margin — the next is `MapGalleryController` at 669 lines, and the median is under 100.

The endpoints fall into segments that have nothing to do with each other operationally: the global
component catalogue authored by the dev tool, the tag catalogue, catalogue transfer between databases,
the player-facing designer, and the pre-defined (system) template catalogue. Nothing but file position
connects them.

The outcome wanted: five focused controllers, arrived at in increments small enough that each one is a
single endpoint, leaves the app working end to end, and is verifiable in seconds.

### Constraint that shapes every increment

Routes come from `[Route("[controller]")]` plus `KebabCaseParameterTransformer`
(`AscendantEmpire.Api/Program.cs:42`). The decision taken is that **routes follow the class name**, so
every unit-design URL changes. Each increment therefore moves one action *and* updates its frontend
call site, its `EndpointAuthorizationTests` row, and the API-surface paragraph in the design doc, in
one commit.

`ApiTestFactory` boots the real API with **no database**
(`AscendantEmpire.Tests/Api/ApiTestFactory.cs:19`). That makes `EndpointAuthorizationTests` the cheap
per-increment gate: it classifies endpoints by route string, so a dropped, duplicated or re-gated
endpoint fails immediately, and an attribute-routing ambiguity surfaces in
`EveryProtectedEndpoint_ReturnsUnauthorized_WithoutAToken`, which issues real requests.

## Target layout

| Controller | Route | Endpoints |
|---|---|---|
| `UnitDesignCatalogueController` | `/unit-design-catalogue` | GET, GET `/{code}`, POST, PUT `/{code}`, POST `/bulk` |
| `UnitDesignTagsController` | `/unit-design-tags` | GET, POST, PUT `/{id}`, GET `/types`, PUT `/types` |
| `UnitDesignTransferController` | `/unit-design-transfer` | POST `/export`, GET `/export/download`, POST `/import` |
| `UnitDesignerController` | `/unit-designer` | GET `/bodies`, GET `/bodies/{ownerComponentId}/slots/{slotId}/components`, GET/POST `/templates`, PUT `/templates/{templateId}`, GET `/templates/{templateId}/compiled` |
| `GlobalUnitTemplatesController` | `/global-unit-templates` | POST, PUT `/{id}`, POST `/recompile-all` |

Each new controller keeps `[ApiController]` + `[Route("[controller]")]`, per-action `[Authorize]`
attributes copied verbatim, `[FromServices] IMediator`, and `response.ToActionResult()` — identical to
the conventions in the current file. No handler, DTO or `ServiceResult` shape changes anywhere in this
work.

### Why these five, and not three

The catalogue, tags and templates are the obvious three. Two segments were pulled out of them
deliberately:

- **Transfer** is `SystemPanel`-gated rather than `EntitySetupTool`, it holds the only two endpoints
  that bypass MediatR and do raw filesystem I/O, and the frontend already files it under
  `features/system/api/catalogTransferApi.ts`. Folding it into the catalogue would keep two auth
  policies and two architectural styles in one file.
- **Global templates** are separated from player templates because they are different resources that
  happen to share a table: `POST /templates` is game-scoped, unlock-checked and player-owned;
  `POST /templates/global` has no game, no unlock check and a unique `Code`.

`UnitDesignerController` is the one deliberate *merge*: the unlock-scoped body/slot reads and the player
template endpoints are six endpoints serving one screen, with one auth posture (`[Authorize]`) and one
identity source (the game token).

## Step 0 — Green the six failing tests ✅

A controller move is a no-behaviour-change refactor whose only proof is a green suite. Six pre-existing
reds made a mistake indistinguishable from the baseline, so this landed first.

**Failing:** `AddingSlotToFittedBodyPreservesExistingSlotsAndFittingsAsync`,
`EditingSlotUpdatesRowInPlaceAsync`, `ReimportWithoutSlotIdsMatchesOnCodeAsync`,
`RemovingSlotDeletesItsFittedTemplateComponentsAsync`, `RenamingSlotCodeWithIdUpdatesInPlaceAsync`,
`UpdateAddingSlotPreservesFittingsAsync`.

**Cause.** UD-31 added a post-save recompile to both component write handlers. It reaches
`AffectedTemplateRecompiler.RecompileAsync`, which sends a `CompileUnitTemplateRequest`
(`AscendantEmpire.Application/Features/UnitComponents/Services/AffectedTemplateRecompiler.cs:104`) and
reads the result. Both fixtures passed a bare `Substitute.For<IMediator>()`, which returns nothing for
it. The path only runs when `templateIds.Count > 0` — i.e. only when a template with a fitted component
already exists. That is exactly those six tests. Every passing test either seeds no template or is
rejected in validation before `SaveChanges`, which is why `SlotIdFromAnotherComponentIsRejectedAsync`
seeds one and stayed green.

**Fix.** Both fixture factories now stub `CompileUnitTemplateRequest` with `ServiceResult<int>.Succeed(0)`.
The comment claiming the stub "makes the post-save recompile a no-op" was true before UD-31 and is not
now, so it was replaced with the reason the stub has to answer.

A test-fixture defect, not a production bug. No `Application` or `Api` change. 34/34 green afterwards.

### Two decisions worth recording

**The folder is `UnitDesigns`, plural.** A singular `UnitDesign` segment collides with the `UnitDesign`
entity type: inside namespace `AscendantEmpire.Tests.UnitDesign.*` the identifier `UnitDesign` binds to
the enclosing namespace and yields CS0118 instead of resolving to the type. Plural also matches
`Domain/Entities/UnitDesigns` and `BackendContracts/UnitDesigns`.

**`UnitDesignSeed` does not create the components.** It only fits the weapon into the body's first slot
and returns the ordered slot ids. Each fixture still creates its components through the handler it is
testing — the bulk importer in one case, the single-component create endpoint in the other — and that
difference is the point of the fixture, not incidental duplication.

**The permission assertion is not vacuous, and it is worth knowing why.**
`PermissionGatedEndpoints_Return403_ForATokenMissingThatPermission` iterates the *discovered* endpoints

against the classified set with `BeEquivalentTo` — bidirectional, so a key naming a route that does not
exist fails just as loudly as an unclassified endpoint. The two tests together are the guarantee; neither
is sufficient alone.

## Known gaps — flag, do not fix here

1. **Four endpoints carry no permission gate**, with a standing `TODO: lock down before any non-dev
   deployment`: `GET catalogue`, `GET catalogue/{code}`, `GET tags`, `GET tag-types`. They are *not*
   reachable anonymously — having no `[Authorize]` attribute means the `FallbackPolicy` applies, so they
   still answer a tokenless request with 401, and `EndpointAuthorizationTests` lists all four under
   `AuthenticatedOnlyEndpoints`. What they lack is a *permission* check, so any logged-in account can
   read the whole dev catalogue. The split makes gating them a one-line class-level attribute later;
   doing it now would change behaviour mid-refactor and break the Entity Setup Tool. Their XML remarks
   all say "intentionally left unauthorized", which is the wrong word for the same reason — worth
   correcting in one small commit. Raised as **UD-35**, which folds in the wording fix because that work
   deletes or rewrites those comments anyway.
2. **`CatalogExportExecutor` and `CatalogImportExecutor` have no tests at all** — hence the empty
   `Transfer/` folder. Worth its own ticket.
3. **The tag-type endpoints have no handler tests** — `UpsertTagTypesHandler` validates shape, rejects
   duplicate enum keys and upserts, all untested. An `InMemoryTestBase`-tier gap.
4. **`GetFullCatalogHandlerTests` is a smoke test** — it asserts roughly 7 of ~44 leaf properties, and
   `DesignSlotRule`, `DesignArmour` and `DesignTemplateComponent` are never exercised because the seed
   contains nothing that populates them. Raised as **UD-33**, which was widened to cover the
   per-component read as well — see gap 8.
5. **The unlock-scoped designer feed is unused** (D1/D2 have no caller). Either the designer should move
   onto it, or it should be deleted. A real decision, not refactor scope. It is also the prerequisite
   for **UD-35**: gating the catalogue reads is impossible while the player-facing designer loads
   through them, and the feed is not a straight swap because the designer's other host — the Entity
   Setup Tool — has no game context and would get a 403 from `TryGetGameContext`.
6. **Test tiers — settled.** Six of the eight unit-design fixtures inherit `SqlServerTestBase`. The open
   question was whether the catalogue fixtures could drop to tier 2 under [testing.md](../testing.md); a
   throwaway `InMemoryTestBase` spike answered it on EF Core 10.0.9 and was then deleted. **Complex types
   really are tier-3**: writes succeed, but any query that materialises *or* projects an entity owning a
   `ComplexProperty` throws `KeyNotFoundException` out of the in-memory query shaper. Since
   `DamageProfile` sits on `UnitComponentWeapon.Attack` and `UnitComponentArmour.Resistance`, and both
   catalogue reads plus every write test dereference it, all of A1–A5 stay on `SqlServerTestBase`.
   **1:1 shared-PK extensions are not a factor** — those work in memory, so the doc and three fixture
   remarks that named them were wrong and have been corrected. `GetPlayerTemplatesHandlerTests` (D3)

   drown the one-endpoint-per-commit diffs.
